# Digital Menu — QR-scannable web menu (Vietnamese/Thai restaurant)

## Context

Guests at a table have to flag down a waiter to get a menu. The goal is a web page they
reach by scanning a QR code on the table: real categories they can tap through, dish
descriptions and prices — not a PDF scan.

Scope is **display only**. No ordering, no payments, no accounts. A chatbot that answers
questions about the menu is wanted later, so `menu.json` is designed now to double as
that chatbot's knowledge base — but nothing chatbot-related gets built yet.

Seven page scans were uploaded to `menu/` (1131×1600 each): six food pages and one EU
allergen legend. They have been read in full; the inventory below is what they contain.

**Decisions locked:**

| Decision | Choice |
|---|---|
| Stack | Plain HTML/CSS/JS + `menu.json`. No build step, no npm, no dependencies. |
| Language | Czech only, prices in Kč. |
| Dish tap | Modal / bottom sheet. |
| Hosting | GitHub Pages. |
| Photos | Cropped out of the page scans. |
| Allergens | Included, plus a legend screen. |
| Dish flags | Spicy indicator. |
| Categories | Fixed by the user — see below. |
| **Visual design** | **Deferred** — user is designing a system in Claude Design and will send it with inspirations and a chosen direction. |

## Menu structure — 32 dishes, 6 categories

Categories as specified by the user. Dish numbers are kept exactly as printed — staff and
regulars order by number, so renumbering would break the restaurant, not just the site.
Within each category, dishes stay in ascending number order.

| Category | Dish numbers | Count | Price range |
|---|---|---|---|
| Předkrmy | 1, 2, 3, 4, 5, 5A | 6 | 50–80 Kč |
| Polévky | 6, 7, 8, 9, 13, 14, 15 | 7 | 30–160 Kč |
| Nudle | 10, 11, 16, 17, 18, 19, 20, 21, 32 | 9 | 100–155 Kč |
| Rýžová jídla | 12, 22, 23, 25, 31 | 5 | 110–220 Kč |
| Vegetarián | 26, 28 | 2 | 130 Kč |
| Křupavá | 29, 33, 34 | 3 | 125–210 Kč |
| Nápoje | — | pending | user is sending the drinks list |

**Dropped as permanently unavailable: 24, 27, 30, 35.** They are not transcribed at all,
so they cannot leak into the site or the future chatbot.

One note on *Polévky*: it now spans 30 Kč starter soups (6–9) and 110–160 Kč main-course
pho bowls (13–15). Printed number order puts the small soups first, which reads correctly
on its own, so no sub-heading is needed — but the card price is what tells a guest which
is which, so "od 110 Kč" must be visible on the card, not hidden in the modal.

## The structural finding that shapes the data model

**20 of the 32 dishes are not single-price.** They are one base dish with 2–6 priced
variants:

- #13 Pho — kuřecí 125 / hovězí 150 / tofu 115 / zelenina 110
- #12 Červené thajské kari — 6 variants, 110–220 Kč (incl. křupavá kachna)
- #33 Křupavá kachna — 5 side variants, 190–210 Kč
- #4 Crunchy Shrimps — 3ks 50 / 5ks 80 (a *quantity* variant, not a protein one)

So a flat `price` field is wrong. The model needs `variants[]`, cards show **"od 110 Kč"**,
and the modal carries the full price list. Variants come in three kinds — protein
(kuřecí/hovězí/krevety/tofu/zelenina), quantity (3ks/5ks), and side (s rýží / s hranolky /
se smaženými nudlemi) — so each dish carries a `variantType` the UI labels by.

The remaining 12 dishes are flat-priced: 2, 3, 5, 8, 10, 14, 15, 16, 25, 26, 28, 29.

## Data model — `data/menu.json`

Hand-editable by a non-programmer. One file is the whole menu.

```json
{
  "restaurant": { "name": "?", "currency": "Kč" },
  "allergenLegend": { "1": "Obiloviny obsahující lepek", "2": "Korýši", "…": "…" },
  "categories": [
    {
      "id": "polevky",
      "name": "Polévky",
      "items": [
        {
          "number": "13",
          "name": "Pho",
          "description": "Vývar, rýžové nudle, jarní cibulka, koriandr, červená cibule, chilli, sójové klíčky, citron",
          "image": "images/13-pho.jpg",
          "allergens": [4, 6],
          "spicy": false,
          "variantType": "protein",
          "variants": [
            { "label": "s kuřecím masem", "price": 125 },
            { "label": "s hovězím masem", "price": 150 },
            { "label": "s tofu",          "price": 115, "vegetarian": true },
            { "label": "se zeleninou",    "price": 110, "vegetarian": true }
          ]
        },
        {
          "number": "14", "name": "Pho Tai Lan", "price": 155,
          "description": "…", "allergens": [4, 6]
        }
      ]
    }
  ]
}
```

Flat dishes use `price`; multi-price dishes use `variants[]`. The render layer handles
both, so the file stays as simple as each dish actually is.

## Photos

32 square crops cut from the six page scans into `images/`, named `13-pho.jpg` etc.

**Honest limit:** at 1131×1600 per page, each dish crop lands around 350–450px. That is
crisp on a grid card (~180px CSS at 2×) but slightly soft as a full-width photo in the
modal on a phone. Good enough to launch; swapping in real photos later is a file drop with
no code change. Two of the six pages shoot on white marble and four on black brick, so
crops carry two different backgrounds — how that is reconciled depends on the theme, and
is one thing your design system needs to answer.

## Site structure

```
Desktop/Digital menu/
  index.html            header, category bar, sections, modal, allergen sheet
  assets/css/tokens.css design tokens ONLY — the file your design system replaces
  assets/css/styles.css layout + components, written against tokens
  assets/js/app.js      render, scroll-spy, modal, search, filters
  data/menu.json        THE menu — the only file to edit to change dishes
  images/               32 cropped dish photos
  menu/                 original scans, kept as the source of truth
  tools/qr.html         local QR generator (not customer-facing)
  plan.txt, README.md, CLAUDE.md
```

The tokens/styles split is the point: **every colour, font, radius and spacing value lives
in `tokens.css`.** When your Claude Design system arrives, applying it means editing that
one file — no layout or JS is touched.

## Interaction design

- **Mobile-first**, designed at 390px, breathing into 2–3 columns wider. Every scan is a
  phone at a table.
- **Sticky category bar** — scrollable chips, active chip follows scroll
  (`IntersectionObserver`), tap smooth-scrolls to the section. One long page, no reloads
  over restaurant wifi.
- **Card** — number, name, short description, photo, "od 110 Kč" or a flat price, spicy
  and vegetarian marks.
- **Modal** on `<dialog>` (free focus trap + Esc) — large photo, full description, the
  complete variant price list, allergen numbers that tap through to their meaning.
- **Search** — one input filtering across all categories, matching dish name, description
  **and number**, since guests and staff say "dvacet dva".
- **Two filters** — *vegetariánské* and *pikantní*. The Vegetarián category holds the two
  fully meat-free dishes (26, 28); the filter is what surfaces the ~12 dishes in other
  categories that have a tofu or zelenina variant, which is otherwise invisible.
- **Allergen legend** — a sheet reachable from the header, transcribed from scan 7.

Phases A and C do not depend on the design system; only B does.

**Phase A — data and structure (can start now)**

   Produce the typo list for your approval.

**Phase B — visual skin (when your design system + inspirations arrive)**

9. `tools/qr.html` generates the table QR from the live URL.
10. `git init`, push to GitHub, enable Pages, generate the QR against the real URL.

2026-09-17 — Router fix: non-route hashes on first load
  Symptom: a tab still holding the old-style anchor "#predkrmy" reloaded into the new
  build and rendered the category index AND all six categories stacked underneath it.

  Cause: readRoute returned null for any hash not starting with "#/", and showRoute
  treated null as "leave the current view alone". That is right for the skip link's
  "#obsah" mid-session, but on the initial render nothing has been hidden yet, so
  "leave alone" meant "show everything".

  Fix: showRoute takes a `first` flag — on the initial render a non-route hash falls
  back to the index instead of leaving the page untouched. readRoute additionally
  resolves the old plain-anchor form ("#nudle") to the matching category, so links
  and open tabs from the pre-routing version keep working.

2026-09-17 — Dish photography: the run, and what came out of it
  All 32 dishes re-rendered. 30 in six batches of five (gpt_image_2_5, high, 2K, 1:1,
  opaque, two image_references each), plus the two test renders from earlier. Zero
  failed jobs. 96 credits of the 106 spent; 10 left.

  WHAT THE TEST CHANGED
  The first two renders (pho, crunchy-shrimps) came back on visibly different wood —
  one yellower with vertical grain, one lighter with horizontal. That is what put the
  grain clause into the prompt for the remaining 30:
      "a warm light-oak table with the grain running horizontally from left to right,
       no knots and no visible plank seams"
  It worked: the 30 that carry it sit on one consistent surface. The two that do not
  are still the only outliers in the set.

  COLOUR MATCH (free, local, sharp)
  Per image, sample the outer 8% ring at 256x256 and take the MEDIAN per channel —
  median not mean, so a plate or shadow poking into the ring cannot drag the reading.
  Target is the median of those 32 readings (219,168,98), so no single image defines
  the look. Apply a per-channel linear gain, clamped to [0.85, 1.18] so a bad reading
  can never wreck an image. Most needed under 5%; the worst were spicy-soup 15%,
  fried-rice-young 14%, bun-nem 13%, tom-yam 13%.
  Note the gain is global, so it shifts the food slightly too. That is deliberate —
  it behaves like a white-balance correction rather than a background-only patch,
  which would leave the dish looking pasted on.
